サービスの役割

Pictor は、描画オブジェクトの一元管理と最適な描画パイプラインの自動選択を担う レンダリングパイプラインモジュール。consumer（上位アプリ／ゲーム）は、描画したいものを ObjectDescriptor という統一フォーマットで登録するだけでよい。Pictor が内部で Static / Dynamic / GPU-Driven へ分類し、カリング・ソート・バッチング・パス実行までを 高効率（DoD）に実行する。

🎯

統一入力

すべての描画対象を ObjectDescriptor で受理。consumer は内部レイアウトを 意識しない（境界 API は OOP、内部は DoD）。

🧭

自動パス選択

PipelineProfile により Forward / Forward+ / Deferred / Hybrid を切替。 プロファイルは JSON で外部設定可能。

⚙️

最下層基盤

Vulkan / GLFW / 標準ライブラリのみに依存。上位ライブラリを取り込まない レイヤ規律を保つ。

主な特徴

Data-Oriented Design (DoD)

全オブジェクトデータは構造体でなく、同一インデックスで紐付く並列配列 （SoA ストリーム）で保持。hot path は flat array + cache-line 整列 （alignas(64)）。scatter（map / 個別 new / pointer chase）を排除。

多段カリング

WorldPartition 広域グリッド → FlatBVH（binned SAH + van Emde Boas レイアウト）詳細 → GPU Hi-Z occlusion。CPU 側は外部数学ライブラリ非依存。

O(n) バッチング

shaderKey から Radix Sort で draw batch / indirect を生成。 実データ移動なし（key-index ペアのみソート）。

GPU-Driven パイプライン

compute update → cull → LOD select → indirect compaction。GPU がドローコマンドを生成。

グローバルイルミネーション

ランタイム GI（CSM シャドウ / SSAO / Light Probe）と、静的オブジェクトの オフライン GI ベイク（Shadow / AO / Irradiance / Lightmap）。

マテリアル & ポストプロセス

Fluent API の PBR マテリアル（パス別バリアント自動生成）。実 Vulkan の host-driven post-process チェーン（Bloom / ToneMapping / Vignette / ColorGrading / DoF）。

テキスト & アニメーション

自前 TTF/OTF パース + 3 描画経路（atlas / image / SVG）。 Skeleton/IK + FBX/BVH import + 2D/Rive/Lottie/Vector アニメ。

マルチバックエンド / 移植性

Vulkan（Win32/X11/XCB/Wayland/macOS/Android）に加え、Emscripten 向け WebGL2 代替 バックエンドと、WASM/N-API 向け C ABI エクスポート。

設計

3 層パイプライン

レイヤ間のデータ受け渡しは SoA ストリームの参照（ポインタ + count）で行い、コピーを最小化する。

┌─────────────────────────────────────────────────────────┐
│  Front-End Layer (オブジェクト管理)                      │
│  ObjectClassifier → 分類 → Pool配置 (Static/Dynamic/GPU)│
└───────────────────────┬─────────────────────────────────┘
                        │ SoA ストリーム参照
┌───────────────────────▼─────────────────────────────────┐
│  Middle Layer (バッチング・ソーティング)                  │
│  shaderKey読取 → Radix Sort O(n) → RenderBatch生成       │
└───────────────────────┬─────────────────────────────────┘
                        │ RenderBatch
┌───────────────────────▼─────────────────────────────────┐
│  Back-End Layer (コマンド発行)                            │
│  PipelineProfile → RenderPass実行順決定 → DrawCommand発行 │
└─────────────────────────────────────────────────────────┘

フレーム実行フロー

data(asset) → scene(SoA store) → update(transform) → culling → batch → gpu(driven)
            → render passes [ gi(shadow/AO/probe) → decal → post-process ]
surface / memory / shader / text は横断基盤、webgl は Vulkan と並行の代替バックエンド
  1. BeginFrame — GPU Fence 待機、Frame Allocator リセット
  2. UpdateScheduler — プール種別に応じ CPU並列 / Non-Temporal / GPU Compute を選択
  3. CullingSystem — 広域 → BVH → GPU Hi-Z の多段カリング
  4. BatchBuilder — sortKey 生成 → Radix Sort → RenderBatch 構築
  5. RenderPassScheduler — プロファイルに基づくパス実行と DrawCommand 発行
  6. EndFrame — GPU submit + present、プロファイラ統計集約

設計原則（OOP 境界 + DoD 内部 + SOLID）

境界は OOP / 内部は DoD

公開 API は class + virtual interface（Handle / Material / RenderPath）で 「データ表現の自由度」を保ち、consumer に内部レイアウトを漏らさない。内部実装は SoA の DoD。

Open/Closed — Registry で拡張

新しい描画パス / Material kind は既存 switch への case 追加ではなく、 継承 + Registry 登録で増やす。

Interface Segregation

太い IRenderer ではなく ICuller / IShader / ICustomRenderPass / IBatchPolicy 等に分離。

Dependency Inversion

consumer は Pictor の抽象 interface に依存。Vulkan handle / GLFW を直叩きさせず Pictor 内部で wrap。

正直な系統分離。 Pictor の spec は「宣言データ（系統A）」と「実描画（系統B）」を明確に区別し、 未配線の領域を誇張せず記述する。詳細は レビュー: 系統A/系統B の補足。

クイックスタート

#include <pictor/pictor.h>

RendererConfig config;
config.initial_profile  = "Standard";
config.profiler_enabled = true;

pictor::PictorRenderer renderer;
renderer.initialize(config);

// オブジェクト登録
ObjectId id = renderer.register_object(desc);

// 毎フレーム
renderer.begin_frame(delta_time);
renderer.render(camera);
renderer.end_frame();

ビルド: cmake -B build → cmake --build build （要 CMake 3.20+ / C++20 / AVX2、Vulkan SDK は GPU 機能に推奨）。 用途別ビルドは spec/setup/ 参照。
