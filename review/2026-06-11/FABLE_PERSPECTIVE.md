# Fable がコードを見る視点 — レビュー観点の記録 (2026-06-11)

このドキュメントは、Claude Fable 5 (`claude-fable-5`) が Pictor の全量診断で実際に用いた視点・優先順位・手法を、本レビューの具体例とともに記録したもの。次回以降のレビュー再現や、人間レビュアーとの観点合わせに使う。

---

## 1. 前提の置き方: 「何を信頼しないか」から始める

コードを読む前に、まず**信頼境界 (trust boundary) を定義**する。Pictor の場合:

- フォント / FBX / BVH / Lottie / visus JSON / pipeline profile = **攻撃者が用意し得る入力** (上位レイヤが CDN・UGC 経由で供給する設計だから)
- C API の引数 = 信頼できない (FFI 越しの呼び出し側のバグも「入力」)
- 自プロジェクト内の呼び出し = 契約違反はバグだが脆弱性ではない

この境界設定が評価を分ける: 同じ「境界チェックなし」でも、ファイル由来の値なら High (V-1/V-2)、内部 API の引数なら Medium (M-1: swap_and_pop) になる。**過去レビューが脆弱性 A だったのは差分だけ見ていたからで、信頼境界を先に引いてから全量を読むと評価が変わる** — これが今回スコアが動いた最大の理由。

## 2. 「コメントの約束」と実装を突き合わせる

コメント・命名・ドキュメントは「実装がこうあるべき」という**検証可能な主張**として読む。今回の主要発見の多くはこの突き合わせから出た:

- 「§12: Fence wait + reset」とコメントされているが fence 待機がどこにもない (H-3)
- 「ring buffer」と命名されているが実体は全域即時リセット (H-3)
- 「Update to temporary first」とコメントされているが同一アドレスを stream し直すだけ (L-3)
- ヘッダが「例外を投げない」と宣言するが `resize(num_props)` が bad_alloc を投げる (V-6)
- `MemoryConfig::use_large_pages` という設定 API が存在するがどこからも読まれない (L-8)
- `get_frame_stats()` が返す draw call 数の供給元 `CommandEncoder::encode()` に呼出箇所がゼロ (D-2)

**手法**: 安全性・性能を主張するコメントを見つけたら、その主張を成立させる行を必ず探す。見つからなければ「虚偽コメント」として実装バグと同格以上 (読み手を誤誘導するぶん悪質) に扱う。

## 3. 並行性は「証明できるか」で読む。雰囲気で通さない

- 条件変数は「述語の状態変更・評価・notify がすべて同一 mutex 下にあるか」を機械的に確認する。1 箇所でも mutex 外の notify があれば lost wakeup を疑い、ウィンドウを構成してみる (→ C-1)。
- atomic だから安全、ではない。`pending_tasks_` は atomic でも、**condvar の待機述語として使う限り mutex 規律が必要**。
- 「このコードパスは毎フレーム実行されるか」で深刻度を決める。C-1 は競合ウィンドウが狭くても 60fps × 毎フレームで踏むため Critical。

## 4. ライフタイムは「誰がいつ無効化するか」を時系列で追う

- FrameAllocator / リングバッファ / swap-and-pop など**一括無効化するメカニズム**を見つけたら、その無効化タイミングと、領域を指したまま残るポインタ・インデックスを総当たりで突き合わせる (→ M-5 sorted_indices_、M-11 WorldPartition の stale index、H-3 in-flight GPU 参照)。
- GPU は「CPU が free した後も N フレーム読み続ける別スレッド」として扱う。CPU 側のライフタイム解析に flight_count を掛け合わせる。
- リソース取得と解放の対称性: コンストラクタ/デストラクタだけでなく **move 代入・エラーパス・部分初期化**の 3 経路を必ず見る (→ H-2 解放関数ミスマッチ、Q-M2 init 失敗リーク、Q-M6 shader module リーク)。

## 5. 整数演算は「最悪の値」を代入して読む

- 境界チェック `a + b > size` を見たら、a, b に型の最大値を代入してラップを確認する (→ V-2)。
- 符号変換 (`int → uint32_t`)、デクリメント (`size - 1`)、`hardware_concurrency() - 1` のような「0 のとき」を必ず試す (→ V-7, M-1, M-8)。
- ファイル由来のカウントは「確保量の上限」とセットでないと信用しない (→ V-4, V-6, V-9)。

## 6. 「動いているように見えるスタブ」を実装と区別する

- 機能の実在性は「呼ばれているか (grep)」「結果が使われているか」「エラーが報告されるか」の 3 点で判定する。コンパイルが通る・初期化が成功する、は実在の証拠にならない (→ D-2 managed 経路、Q-2 iOS surface、c_api.cpp がビルド対象外)。
- スタブ自体は開発過程として正当。問題は**スタブの出力が公開 API (統計・戻り値) に本物として流れ込む**こと。そこだけを指摘対象にする。

## 7. プロジェクト自身のルールを評価軸にする

- CLAUDE.md / ヘッダに明文化された不変条件 (「hot path に string/map ゼロ」「frame 内再 alloc 禁止」) は、一般論より**優先度の高いレビュー基準**として使う。同一コードベース内の矛盾 (CompiledGraph は規約遵守、Profiler は違反) は説得力のある指摘になる (→ D-3, M-1)。
- per-frame か init-time かを必ず区別する。init の `unordered_map` は指摘しない。違反は「hot path で」のみ数える。

## 8. 過去レビューへの説明責任 (regression tracking)

- 前回指摘を 1 件ずつ「修正 / 未修正 / 指摘自体が誤り」に分類して追跡する (→ 9 件中 0 件修正、うち 1 件は前回提案が実施不能と判明: SkinnedVertex の alignas は GPU layout を壊す)。
- **前回提案の誤りを発見したら、それも記録する**。レビューの信頼性はここで決まる。

## 9. 指摘の作法: 反証可能性と優先順位

- すべての指摘は **file:line + 故障シナリオ + 修正方向**の 3 点セット。実コードを読んで行番号を検証できないものは報告しない (推測の指摘はノイズ)。
- 深刻度は「踏む頻度 × 影響」で決める。理論上の UB でも毎フレーム踏むなら Critical、攻撃前提が必要なら High、opt-in 機能内なら Medium。
- **良い実装を明示的に記録する** (DEFLATE の距離検証、PoolAllocator の整列規律、swap-and-pop の id 付替え等)。理由は 2 つ: (1) 修正時に壊してはいけない箇所の地図になる、(2) 「全部ダメ」ではなく「どこが本物でどこが穴か」の解像度こそレビューの価値だから。
- 同型の問題はパターンとして束ねる (「JSON パーサ 3 系統の無制限再帰」「VkResult 未チェック群」)。修正側が 1 つの方針 (深度上限ヘルパー、VK_CHECK) で一括対応できる形で渡す。

## 10. 実施プロセス (今回の実際)

1. リポジトリ構造・規模 (40k 行・23 サブシステム)・過去レビュー形式を把握
2. 信頼境界とリスクの濃淡で 4 領域に分割: ①パーサ/入力境界の脆弱性 ②メモリ・並行性 ③設計 (規約準拠 + アーキテクチャ) ④品質 (Vulkan 正しさ・エラー処理・テスト・スタブ判定)
3. 4 エージェントを並列実行。各自に「行番号は実読で検証せよ」「実証できないものは報告するな」「良い点も記録せよ」を課す
4. 結果を統合し、領域横断のテーマ (虚偽コメント / 二重アーキテクチャ / 信頼境界未定義) を抽出
5. 過去レビューのスコア基準と接続し、スコア変動の理由 (測定方法の変化) を明記

### 視点の要約 (1 行ずつ)

| 視点 | 一言で |
|---|---|
| 信頼境界 | 「このバイト列は誰が書けるか」を先に決める |
| コメント検証 | コメントは主張。主張には証拠行を要求する |
| 並行性 | condvar は mutex 規律を機械的に検査。雰囲気で通さない |
| ライフタイム | 一括無効化メカニズム × それを指す全ポインタの総当たり |
| 整数 | 最悪値 (MAX, 0, 負) を代入してから境界チェックを信じる |
| スタブ判定 | grep で「呼ばれているか」。コンパイル成功は実在の証拠でない |
| 規約準拠 | プロジェクト自身のルールを最優先の物差しに使う |
| 追跡 | 前回指摘の生死を数え、前回の誤りも認める |
| 作法 | file:line + シナリオ + 修正方向。良い点も地図として残す |
