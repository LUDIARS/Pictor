### 空 — 大気散乱と夜空（p.11〜17）

空の色は、太陽光が空気中の粒子に当たって散らばる（散乱する）ことで決まります。講演では、この物理計算は変えずに、係数と色をデザイナーが調整できるようにしていました。

#### p.11「空」— 朝・昼・夜で色味が全然違う

スライド：[p.11](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p11)

朝と夕方は太陽や雲が赤くなり、昼は青空が広がり、夜は真っ暗で月が見えます。光源は同じ太陽なのに色が違うのは、太陽の高さによって光が通る空気の量が変わるからです。次の 3 枚で、その理由を説明しています。デモでは、時刻（SkyTime）から太陽の向きを決めています。

**コード**：[`sky_profile.cpp` sun\_direction（L94）](sky_profile.cpp#L94-L99) 　**デモ**：Scene 1 で `[` / `]` キーを押して時刻を動かす

#### p.12「大気散乱」— 太陽光が粒子にぶつかって散らばる

スライド：[p.12](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p12)

右の図は、太陽光が空気中の粒子（黒い点）に当たって四方八方に散り、その一部が目に届く様子です。空を見るということは、視線の先にあるたくさんの粒子から散ってきた光を集めていることです。夜に空が真っ黒なのは、そもそも散乱させる光源がないからです。

コードではこれをそのまま計算します。視線を 16 段に区切って進み、各地点で「そこまで届く太陽光 x 目の方へ散る割合 x 目までの減衰」を足し合わせます。スライドの「2 つの種類」が、次のレイリー散乱とミー散乱です。

**コード**：[`atmosphere.glsl` atmosphere\_raw（L55〜）](shaders/atmosphere.glsl#L55-L106)。視線を進むループは L75、太陽までの減衰を求める内側のループはその中

#### p.13「レイリー散乱」— 青ほど散り、道のりが長いと赤が残る

スライド：[p.13](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p13)

空気の分子のような小さな粒子では、波長の短い青ほど強く散乱します（波長の 4 乗に反比例）。図の左は昼で、太陽が真上にあるため光が通る距離が短く、青が残って空一面から青が届きます。右は夕方で、通る距離が長く、途中で青が散らされて先に失われ、残った赤が届きます。

コードでは、散乱係数を波長から計算しています（通る距離が長いほど、exp で減衰が大きくなる）。光がどの向きに散るかは、位相関数で決めます。

**コード**：[散乱係数 rayleigh\_beta（L20）](shaders/atmosphere.glsl#L18-L23) / [位相関数 phase\_rayleigh（L28）](shaders/atmosphere.glsl#L27-L28) 　**デモ**：Scene 1 の Z（Rayleigh）、Wavelength R/G/B

#### p.14「ミー散乱」— 前へ強く、どの色も同じように散る

スライド：[p.14](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p14)

塵や水滴のような大きめの粒子では、光は進んできた方向（前方）へ強く散り、色による差がありません。だから、届いた光の色がそのまま散ります。昼は白い光が散って遠くが白く霞み、夕方は（青が抜けた）赤い光が散って遠くや雲が赤く染まります。図の矢印の色が、届いた光の色です。

**コード**：[散乱係数 mie\_beta（L25）](shaders/atmosphere.glsl#L24-L25) / [前方への偏り phase\_mie（L30）](shaders/atmosphere.glsl#L29-L36) 　**デモ**：Scene 1 の X（Mie）、Mie Directionality g

#### p.15「Unity 上で再現」— 計算はそのまま、係数をデザイナーが触る

スライド：[p.15](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p15)

左がレイリー散乱だけ、右がミー散乱を加えた空です。右側のインスペクタに並ぶ値が、デザイナーが触れる係数です。デモでは次の名前に対応させています。

**コード**：[`sky_profile.h` AtmosphereSettings](sky_profile.h#L36-L44)（値をまとめた構造体）

#### p.16「表現の幅」— 計算結果に色を掛けて、狙った空にする

スライド：[p.16](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p16)

係数だけでは作れない空（右の赤い月の夜）は、レイリーとミーの「計算結果」に、それぞれ Rayleigh Color / Mie Color を掛けて作ります。左下のグラデーションは横軸が時刻（0〜24 時）で、時刻ごとに掛ける色が変わります。物理計算の滑らかな色の変化を残したまま、色味だけを寄せられます。

**コード**：[色を掛ける所 sky\_color\_ex（L109〜）](shaders/atmosphere.glsl#L109-L125) / [時刻ごとの Rayleigh / Mie Color のキー](sky_profile.cpp#L57-L70) 　**デモ**：Scene 1 の C（Tint）

#### p.17「夜空」— 星と天の川、瞬き、時刻のカーブ

スライド：[p.17](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p17)

星と天の川は、空に貼ったテクスチャを回転させて作ります。回す軸（Star Rotation Axis）と 1 日に回る量（Daily Cycle）を調整できます。瞬きは、星のテクスチャに別のノイズを掛け、ノイズだけを UV スクロール（座標をずらして流す）して作ります。星は動かず、掛ける値だけが変わるので、その場で明るさが揺らぎます。インスペクタの Star Flicker Speed、Star Tiling、Star Exposure は、デモにも同じ名前であります。

**コード**：[星のテクスチャ相当 star\_field（L24）](shaders/night.frag#L23-L34) / [回転（L45〜47）](shaders/night.frag#L45-L48) / [ノイズの UV スクロールと瞬き（L52〜55）](shaders/night.frag#L52-L55) 　**デモ**：Scene 2 の C（星｜ノイズ｜掛けた結果 の分解表示）

右のウィンドウは Galaxy Intensity のカーブで、横軸が 0〜24 時、縦軸が強さです。キーは 0:00 = 1、1:30 = 1、2:00 = 0、23:31 = 0、24:00 = 1 で、深夜の 23:31〜2:00 だけ天の川が見えます。デモにも同じキーを入れています。

**コード**：[天の川の帯（L57〜64）](shaders/night.frag#L57-L67) / [Galaxy Intensity のキー](sky_profile.cpp#L86-L90) 　**デモ**：Scene 2 で 0:00 前後を `[` / `]` で行き来する

#### 用語の補足（空）

| 用語 | 意味 |
| --- | --- |
| 波長 | 光の色を決める「波の長さ」。赤は約 680nm、緑は 550nm、青は 450nm。スライドの Wavelength 680/550/450 は、R/G/B を代表する波長 |
| 散乱係数 | 1m 進むごとに光がどれだけ散らばるか。レイリー散乱では波長の 4 乗に反比例するので、450nm の青は 680nm の赤の約 5.2 倍散乱する |
| 位相関数 | 散乱した光がどの向きにどれだけ飛ぶかを表す関数。レイリーは前後にほぼ同じだけ、ミーは前方に偏る |
| Mie Directionality Factor（g） | ミー散乱の前方への偏り。一般に g と書かれる。g = 0 で全方向に均等、g → 1 で光が進む方向へ集中する。太陽の周りの光の輪の大きさが変わる |
| 透過率と光学的距離 | 光が大気を通ると、通った空気の「濃さ × 距離」（光学的距離）に応じて指数関数的に弱まる。夕方に青が「先に失われる」のはこのため |
| スケールハイト | 空気の濃さが 1/e（約 37%）になる高さ。分子（レイリー）は約 8km、塵や水滴（ミー）は約 1.2km と低い所に集まる。スライドの Kr / Km は定義が説明されていません。名前と値の大きさ（9600 / 7900）から、高さに関わる係数と推測しています |
| 単一散乱 | 光が 1 回だけ散乱して目に届くと仮定する計算。ゲームの空はほとんどこれで、省いた多重散乱の分は色や強度の調整で補う |
| UV スクロール | テクスチャを読む座標（UV）に時間を足して、絵を流すように動かすこと。星とノイズを別々に動かすと、掛けた結果が方々で明滅する |

#### デモで確かめる（空）

**Scene 1（`sky.frag` / `atmosphere.glsl`）**：17:20 の西の空から始まります。このシーンで変えた大気の設定は、他の全シーンにも引き継がれます。

- Z でレイリー、X でミーを切って、それぞれの役割を見る（レイリーだけだと夕焼けの太陽の周りの光が消える）

* `[` / `]` キーで時刻を動かし、太陽が低いところで赤くなることを確かめる

- Wavelength B を 450 → 550 にする、Mie Directionality g を 0.76 → 0.95 にする
- C で Profile の Tint（Rayleigh / Mie Color）のありなしを比べる

**Scene 2（`night.frag`）**：23:30 の夜空です。

- C（Breakdown）で「星のテクスチャ｜ノイズ｜掛けた結果」を並べて表示する
- Flicker Speed と Rotation Daily Cycle を大きくして、瞬きと日周運動の違いを見る
- V で Profile の Star / Galaxy Intensity カーブを切り、\] で朝まで進める

### 海 — 広い海を低負荷で近景まで美しく（p.18〜21）

このゲームの海は、遠くから眺めるだけでなく、ボートで移動したり釣りをしたりと、近くで遊ぶ場所です。そのため講演では、既存の水面パッケージを土台にして、タイル分割と 3 つのカスタマイズを加えていました。

#### p.18「海」— 遠景ではなく、近くで遊ぶ海

スライド：[p.18](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p18)

左はボートで海を移動する画面、右は岸壁から釣りをする画面です。どちらもカメラのすぐ近くに水面があるので、「遠くから見てきれい」だけでは足りません。それでいて海は広大なので、「広い海を低負荷で、近景まで美しく」が目標になりました。この後の 3 枚が、そのための工夫です。

**デモ**：Scene 4 でカメラを水面ぎりぎり（Q キーで下降）まで下げてみる

#### p.19「海」— 水面はパッケージ（boat-attack-water）が土台

スライド：[p.19](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p19)

波・水深・泡・反射は、Unity のデモ「Boat Attack」の水面パッケージを参考にしています。水面の形は Gerstner 波で、向きと長さの違う波を何枚も重ねて作ります。Gerstner 波は水面の点を上下だけでなく横にも動かすので、波頭が尖ります。水深で色を変え、泡と屈折も付けます。

#### p.21「新たに追加したもの」— 浅瀬・水底の色・ボートの水

| 用語 | 意味 |

#### p.25「草のカリング」— セルで大まかに、ComputeShader で 1 本ずつ

スライド：[p.25](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p25)

#### p.27「草のジオメトリ」— UV に意味を持たせる

スライド：[p.27](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p27)

草のメッシュの頂点には、本来はテクスチャの座標を入れる UV が 2 組あります。そこに別の意味を入れています。

- **UV0.x**：葉の左端が -1、右端が +1。法線（面の向き）を左右に傾け、平らな板ポリに丸みがあるように見せる
- **UV0.y**：根元が 0、先端が 1。風の変位、ひねり、踏み分け、AO、色の重みに使う
- **UV1**：本来のテクスチャ座標

左下の注にあるように、葉の形はテクスチャで切り抜く（カットアウト）のではなく、メッシュの形そのもので作ります（不透過）。モバイルの GPU では、その方が最適化が効いて軽いからです。

デモはメッシュを持たず、頂点番号から葉を組み立てて UV0 を作っています。

#### p.28「活用事例」— UV0.y で風、ねじれ、色、AO

スライド：[p.28](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p28)

左はジオメトリ（形）への使い方です。UV0.y を重みにして、先端は風で揺らし、根元は揺らしません。同じ値をねじれの度合いにも使います。右は材質への使い方です。先端と根元に色を指定してグラデーションさせ、根元を暗くして AO（隙間に光が届きにくい暗さ）を出します。

**コード**：[ねじれ（L63〜66）](shaders/grass.vert#L63-L66) / [風と踏み分けを UV0.y の 2 乗で掛ける（L71〜89）](shaders/grass.vert#L71-L89) / [色のグラデーション、AO、透過光 `grass.frag`](shaders/grass.frag#L20-L33) 　**デモ**：Scene 8 の Twist Amount、Weak Sway、AO

描画までの一連の流れを、デモの実装に合わせて並べると次のようになります。

1. 配置データを作る（本家は Houdini のペイント、デモはノイズと道のマスク）
2. 建物の Collider に入る草を除き、セル番号順に並べ替える。各セルは「開始番号と長さ」だけを持つ
3. 毎フレーム、CPU がセルの箱を視錐台と比べて、見えるセルを選ぶ
4. 見えるセルが連続していれば、範囲をつなげて 1 回の Dispatch にする
5. ComputeShader が草 1 本ごとに視錐台と距離で判定し、LOD0 / LOD1 の可視リストへ追加する
6. GPU が数えた本数のまま、DrawIndirect で描く（CPU は何本残ったか知らなくてよい）

#### 用語の補足（草）

| 用語 | 意味 |
| --- | --- |
| GameObject | Unity のシーン上の 1 つ 1 つの物体。Transform などを持ち、数万個にするとそれだけで重い。草をこれにしないのはそのため |
| カリング | 描いても見えない物を、描く前に捨てること |
| 視錐台 | カメラに写る範囲。先端を切った四角錐の形で、6 枚の平面（左右上下・手前・奥）で囲まれている |
| Bounds / バウンディングボックス | 物体を包む箱（または球）。この箱が視錐台の外なら中身も外と分かるので、判定が安く済む |
| ComputeShader / Dispatch | ComputeShader は、描画ではなく計算だけを GPU で大量に並列実行するプログラム。Dispatch はそれを「この数だけ実行して」と命令すること。命令の回数にもコストがあるので、連続するセルをまとめる |
| インスタンシング / DrawIndirect | 同じ形を位置だけ変えて大量に描く仕組み。DrawIndirect は、描く個数を CPU ではなく GPU 上のバッファから読む描画命令。カリング結果を CPU に戻さずに描ける |
| 法線 | 面が向いている方向。光との角度で明るさが決まる。板ポリは法線が 1 方向しかないので平らに見える。左右の端で法線を傾けると丸みが出る |
| UV0 / UV1 | 頂点に持たせる 2 つの値の組。本来はテクスチャの座標だが、「根元からの高さ」など任意の情報を入れてよい |
| AO（Ambient Occlusion） | 物の隙間や根元など、周りからの光が届きにくい所の暗さ |
| カットアウト | テクスチャの透明度を見て、ピクセルごとに「描く / 捨てる」を決める方法（アルファテスト）。モバイルの GPU では、描く前に隠れたピクセルを捨てる最適化が効きにくくなるので、不透過の方が軽いことが多い |
| 透過光 | 薄い葉を裏から光が透けて明るく見える現象。逆光で草の先端が光る |

### 間接光（GI）— 時刻で変わる照り返し（p.37〜45）

講演では APV を土台にして、「焼くのは光が遮られる量だけ、空の色は実行時に差し替える」ことで、時刻に追従する GI を作っていました。そこに建物ごとの LocalGI を重ね、優先度で使い分けています。

#### p.37「間接光（GI）」— 3 つの方式の比較

スライド：[p.37](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p37)

跳ね返った光（間接光）を事前に計算しておく方式を、「時刻で変えられるか」「広い範囲を覆えるか」「UV が要らないか」で比べた表です。

|  | LightMap | LightProbe | APV（Adaptive Probe Volumes） |
| --- | --- | --- | --- |
| 動的に変化できるか | × 時刻ごとに焼き直し | × ベイクで固定 | ○ Sky Occlusion |
| 広い範囲を覆えるか | △ UV とデータ量 | × 手で置くのは大変 | ○ 囲むだけ |
| UV が不要か | × 必要 | ○ 不要 | ○ 不要 |

LightMap はメッシュの表面に明るさの画像を貼る方式で、専用の UV が要り、時刻が変われば焼き直しです。LightProbe は空間の点に光を保存する方式で、点を手で置くのが大変です。APV はその点を自動で敷き詰め、Sky Occlusion（後述）で時刻にも対応できます。ただし、屋内やライトが多い場所、品質が必要な場所では LightMap を使います。

#### p.44「DynamicReflectionProbe」— ベイクした材質を毎フレーム照らし直す

スライド：[p.44](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p44)

毎フレーム 1 個ずつ、次の 3 段階でプローブを作り直します。

1. **テクスチャを読む**：プローブの地点から 6 方向を見て、そこにある物の材質（Diffuse = 色、Normal = 面の向き、Emission = 自分で光る分）をベイクしておく。光を含まない材質だけを焼くのがポイント
2. **ライティングをする**：その材質を今の太陽で照らし直し、空が写っていた画素は今の空の色に差し替える。それをぼかして mip（縮小画像の列）を作り、表面の粗さ（ラフネス）に応じて段階的にぼかす。これが反射になる
3. **GI を生成する**：プローブごとに別の GI になる。これが LocalGI

デモは Cubemap の代わりに、6 方向それぞれを 1 画素にまとめています（円錐内のレイを平均してぼかしたのと同じ役割）。

スライド：[p.45](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p45)

ある場所の GI は、使えるもののうち一番左を使います。建物の LocalGI の範囲内なら LocalGI、プローブがある場所なら SkyOcclusion x GlobalGI、どちらもなければ GlobalGI です。

#### 用語の補足（GI）

| 用語 | 意味 |
| --- | --- |
| GI（大域照明） / 間接光 | 光源から直接届く光ではなく、空や地面や壁に跳ね返って届く光。影の中が真っ黒にならないのはこれのおかげ |
| LightMap | メッシュの表面に、計算済みの明るさを画像として貼る方式。表面を画像に対応づける専用の UV が要る |
| LightProbe | 空間の点に「そこに届く光」を保存しておく方式。動くキャラクターは近くの点を補間して照らされる |
| 球面調和（SH） | 「どの方向からどれだけ光が来るか」を、数個の数字で大まかに表す方法。プローブ 1 個を少ないデータで持てる。デモは 4 つの数字（L1）を使う |
| Cubemap | 立方体の 6 面に周囲の景色を貼ったテクスチャ。反射や環境光に使う |
| mip / ラフネス | mip は同じ画像を半分ずつ縮めた列。ラフネスは表面の粗さで、粗い物ほどぼけた反射になるので、粗さに応じてよりぼかした mip を読む |
| Diffuse / Normal / Emission | それぞれ、物の色（アルベド）、面の向き（法線）、自分で光る分。光を含まない「材質」だけを焼いておくので、後から今の太陽で照らし直せる |
| 畳み込み | 周りの全方向の色を、面の向きに応じた重みで平均すること。「この向きの面に届く環境光」が求まる |
| Ambient Cube | 6 方向（±X・±Y・±Z）の色だけで環境光を表す簡易版。デモの LocalGI はこれで Cubemap の代わりをしている |

### タレントのライティング — どこにいても可愛く（p.46〜49）

#### p.47「タレント専用のライト」— 太陽そのまま / ズラす / 固定

スライド：[p.47](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p47)

タレントを照らすライトの向きを、背景の太陽とは別に決められます。

- **太陽そのまま**：背景と完全に同じ向き。逆光だと顔が暗くなる

- **固定**：屋内や洞窟のように、太陽と関係ない場所では向きを動かさない

**コード**：[3 つのモード（L120〜123）](shaders/talent.frag#L119-L125) / [影は本物の太陽（L106）](shaders/talent.frag#L104-L107) / [向きを回す rot\_y（L83）](shaders/talent.frag#L83) 　**デモ**：Scene 7 の Light Mode（PgUp / PgDn）、Offset Yaw、Fixed Yaw

#### p.48「輪郭リムと GI 補正」— 可愛く見せるための補正

スライド：[p.48](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p48)

デモのリムは、「輪郭ほど強い（フレネル）」「太陽に向いた縁だけ」「逆光ほど強い」「影では弱める」の 4 つを掛け合わせています。

#### p.51「Unity での実現方法」— DynamicSky と SkyTime

スライド：[p.51](https://www.docswell.com/s/UnityJapan/Z1QGE8-2026-11-17-184813#p51)

**DynamicSky** は、空の時間（SkyTime）を管理するコンポーネントです。毎フレーム、太陽と月の座標を更新し、GI を更新し、Profile から色や値を取得します。

**SkyTime** は 1 日を 0〜1 で持ちます（0:00 = 0.0、6:00 = 0.25、12:00 = 0.5、18:00 = 0.75、24:00 = 1.0）。時刻がただの数なので、Timeline のクリップ A（12:00 = 0.5）とクリップ B（18:00 = 0.75）を weight 0.5 ずつで混ぜると、0.5 x 0.5 + 0.75 x 0.5 = 0.625 で 15:00 になります。weight を掛けて足すだけで、ブレンドがそのまま時刻の補間になります。

**コード**：[時刻から太陽の向き sun\_direction（L94）](sky_profile.cpp#L94-L103) / [クリップのブレンド blend\_clip\_times（L105）](sky_profile.cpp#L105-L107) / [毎フレームの時刻の更新（L628）](main.cpp#L628) 　**デモ**：Scene 9 の Z（Use Clip Blend）、Clip A / Clip B time、Clip B weight

1. **パラメータは「1 日」を表現できる**：色はグラデーション（左から右を 0〜24 時）、数値はカーブ（0〜1 を 0〜24 時）で持つ
2. **「時間で変化」と「固定値」を切り替えられる**：固定値にすると時刻に関係なくその値を使う

| 用語 | 意味 |
| --- | --- |

| HDR カラー | 1.0 より明るい値を持てる色。太陽や電球のように「白より明るい」光を扱える。光の色を Intensity 付きの HDR グラデーションで持つのはこのため |
| Timeline / クリップ / weight | Unity の Timeline は演出を時間軸に並べる仕組み。クリップはその上の 1 つの部品で、重なったクリップは weight（影響の強さ、合計 1）で混ぜられる |

解答の後ろの（　）は、デモで確かめる方法です。

### 1. 空

- **Q1-1** 青がなくなり、白っぽく霞んだ空になる。ミー散乱は波長によらずどの色も同じように散乱し、太陽の周りだけが明るく光る。（Scene 1、Z を OFF）
- **Q1-2** 青も緑と同じ強さでしか散乱しなくなり、空は青緑っぽい白に近づく。レイリー散乱は波長の 4 乗に反比例するので、「青さ」は波長の差で決まる。（Scene 1、Wavelength B）
- **Q1-3** 0.95 では、太陽の周りの光の輪が小さく鋭い点になる。太陽から離れた空の霞みは減る。g = 0 では光が全方向に均等に散り、輪がなくなって空全体が白く霞む。（Scene 1、Mie Directionality g）
- **Q1-4** Rayleigh Color / Mie Color を計算結果に掛ける。物理係数を大きく変えると、昼や夕方を含む全時刻の空が崩れ、色の狙いもつけにくい。色を掛ける方式なら、物理計算のグラデーションを残したまま、時刻ごとに狙った色へ寄せられる。（Scene 1、C）
- **Q1-5** 誤り。赤は一番散乱しにくい。長い大気を通る間に青が散乱されて先に失われ、散乱されずに残った赤が目に届く
- **Q1-6** 星そのものが空を滑って移動するだけで、その場で瞬かない。星は動かさず、掛け合わせるノイズの方だけを動かすのがポイント。（Scene 2、C の分解表示）
- **Q1-7** Star Intensity のカーブ。昼の間のキーを 0 付近（スライドでは 5:56 と 18:00 が 0.05）にする。「固定値」になっていないかも確かめる。（Scene 9、C）

### 2. 海

- **Q2-1** Q = 0 では点が上下にしか動かず、丸い正弦波になる。大きすぎると波頭で面が自分自身を追い越して折り返し、尖ったループ状の破綻が出る。デモは Q に上限を設けている。（Scene 4、Wave Steepness Q）
- **Q2-2** GPU から CPU への読み戻しは、GPU の完了待ちや数フレームの遅れが出て重い（特にモバイル）。講演では、同じ Gerstner の式を CPU でも計算して波の高さを取得している。（`gerstner_cpu.h`）
- **Q2-3** 頂点が膨大になる（1km 四方なら約 400 万頂点）。遠くは細かさが無駄で、間隔を広げると近くが粗くなる。講演では 20m のタイルを敷き、視界の中を近い順に細かく分割し（Job + Burst で並列化）、遠景は平面にしている。（Scene 4、V）
- **Q2-4** 波がある所で突然平らになり、境目に線が見える。デモでは Wave Fade Start から Wave Fade End にかけて振幅を徐々に 0 にしている
- **Q2-5** 波が弱まり始める場所が沖側へ広がる。振幅の倍率は「水深 ÷ Shallow Depth」なので、水深 5m の所は 3m 設定では 100%、10m 設定では 50% になる
- **Q2-6** 船に付けたボリュームをステンシルに書き、その範囲の水面を描かない。（Scene 4、C）
- **Q2-7** 太陽の反対側を向いた船体の側面など、光が当たらないはずの面にも網目が出る。（Scene 4、M）
- **Q2-8** 太陽光の色と強度に追従させていない。追従させれば、太陽が沈むと一緒に消える。（Scene 4、N）

### 3. 草

- **Q3-1** 物体ごとの更新、カリング、描画命令の準備、メモリが CPU 側で重くなる。講演では草を GameObject にせず、配置データをそのまま GPU へ渡している
- **Q3-2** 配置データをセル番号順に並べているので、同じセルの草は配列の中で連続しているから
- **Q3-3** 2 回。セル 2 と 3 は連続しているので 1 回にまとめ、セル 5 は別に 1 回。（Scene 8 の HUD）
- **Q3-4** セルが少しでも映れば、そのセルの画面外の草や遠すぎる草まで頂点処理され、無駄になる。逆にセル判定なしで 1 本単位だけにすると、毎フレーム全部の草を判定する無駄が出る。（Scene 8、Z）
- **Q3-5** 大きい Collider で消えた草は、今のデータからはもう失われている。そのため、完成後も建物の周りに草のない穴が残る。元の配置データから再計算すれば戻る。（Scene 8、N を OFF にして G）
- **Q3-6** 根元まで動いて、草が地面から浮いたり滑ったりする。UV0.y（の 2 乗）で重み付けすると、根元は固定され先端ほど揺れる
- **Q3-7** テクスチャを読んでからでないと描くか捨てるか分からないので、隠れたピクセルを先に捨てる最適化（深度の先行判定やタイル GPU の隠面消去）が効きにくくなる。重なった草の描き込みが増えて重くなる
- **Q3-8** 描く草も判定する草も減って軽くなる。ただし 60m より先は地面だけになるので、遠景がさみしくなる。地面の色を草に寄せて境目を目立たなくする。（Scene 8、Fade End）

### 4. 空気感と雲

- **Q4-1** 時刻と方向によって霞の色が自動で変わり、空とつながる。夕方は太陽側がオレンジ、反対側は青く霞み、夜は暗く霞む。固定の灰色だと、夕方や夜に遠景だけ浮いて見える
- **Q4-2** 筋に段々の縞模様（バンディング）が出る。サンプルの開始位置をピクセルごとにランダムにずらすジッターを使うと、縞が細かいノイズに変わって目立たなくなる。（Scene 3、Sample Count と V）
- **Q4-3** 太陽が画面の外（カメラの後ろ）にあるので、画面上で太陽に向かって進むこの方式では計算できず、シャフトは消える。画面に写っている情報だけを使う方式の限界
- **Q4-4** 板の法線は 1 方向なので、雲全体が同じ明るさになり、段ボールのように平らに見える。太陽が後ろに回ると雲全体が真っ暗になる。SixWay は、体積を光がどう通るかを方向ごとに焼いているので、厚い所と薄い縁で明るさが変わる。（Scene 5、Z）
- **Q4-5** Positive テクスチャの B チャンネル（奥）。縁の薄い所ほど光が透けて明るくなる。（Scene 5、V）
- **Q4-6** 太陽光は地面や建物、タレントも照らしているので、全部が赤くなってしまう。向きは太陽のままで、色と強度だけ別の「雲専用ライト」を使う。（Scene 5、C）
- **Q4-7** 光る範囲が太陽のすぐ周りに絞られる。太陽に近い雲だけが光る。（Scene 5、Forward Power）

### 5. 間接光（GI）

- **Q5-1** 時刻ごとに焼き直しが要る（または時刻の数だけ LightMap を持つ）。さらに、全メッシュに専用 UV が必要で、広い範囲ではデータ量も膨らむ
- **Q5-2** GI がベイクした時刻の色で固定され、夜になっても昼の青い照り返しが残る
- **Q5-3** 実行時に置かれた建物はベイクに入っていない。そのため、ベイクした時の形のまま光が抜ける。（Scene 6、N）
- **Q5-4** 下を向いた面（あごの下、腕の内側、スカートの裏）が空の青で照らされ、不自然に青くなる。（Scene 6、X）
- **Q5-5** LocalGI。プールにプローブを置き、ネオンの光を Emission として焼いておくと、その場所だけネオンの色の GI になる。（Scene 6、ショップの電球）
- **Q5-6** 光を含まない材質だけを焼いておけば、今の太陽と空で毎フレーム照らし直せるから。照明済みの色だと、ベイクした時刻の光で固定されてしまう
- **Q5-7** Local Blend Dist（影響範囲の端で混ぜる幅）を広げる。（Scene 6）
- **Q5-8** 何もない所では間接光が場所であまり変わらないので、粗くても品質が落ちない。その分、メモリとベイク時間を節約できる。物の近くは遮蔽や照り返しで急に変わるので、細かく置く

### 6. タレントのライティング

- **Q6-1** 顔が影側になって暗くなる。「太陽からズラす」モードで、背景と馴染ませたまま顔に光を回す。（Scene 7、Light Mode 1）
- **Q6-2** 洞窟には太陽が届かないのに、時刻と一緒にキャラクターの光の向きが回り、不自然に陰影が動く。屋内や洞窟では「固定」を使う
- **Q6-3** 光の向きと無関係に輪郭全体が光り、「発光する縁取り」に見える。太陽がどちらにあるか分からなくなる
- **Q6-4** リムの幅が細くなり、輪郭のごく端だけが光る。（Scene 7、Rim Power）
- **Q6-5** 太陽光が届かないはずの場所で、太陽のリムだけが光っている。影に入ったらリムの色を減衰させる。（Scene 7、C と Rim In Shadow）
- **Q6-6** 背景の GI が持っている時刻や場所の雰囲気が消え、景色全体がくすんだ灰色に寄る。肌の血色だけは保ちたいので、肌（タレント）にだけ掛ける。（Scene 7、X）

### 7. 24 時間ライティング

- **Q7-1** 0.8 x 24 = 19.2 時間 → 19:12
- **Q7-2** 0.25 x 0.25 + 0.75 x 0.75 = 0.625 → 15:00。（Scene 9、Z）
- **Q7-3** (23/24) x 0.5 + (1/24) x 0.5 = 0.5 で、12:00 になって真昼が一瞬入る。0:00 をまたぐと「時刻 x weight の和」は破綻する。避けるには、1:00 を 25:00 として扱って混ぜ、結果を 24 で割った余りにする（24:00 = 0:00）。または、0:00 をまたぐクリップを重ねない。（Scene 9、Clip A = 23、Clip B = 1）
- **Q7-4** 6 時間かけて黒 → 白へ単調に変わるので、朝焼けや夕焼けの赤い時間がほとんどなくなる。色が速く変わる朝と夕方に、キーを集中させる
- **Q7-5** そのパラメータを「固定値」に切り替える。固定値は時刻に関係なく使われる。（Scene 9、X / C / V）
- **Q7-6** SkyTime を等速ではなく動かす。Timeline の Time Control Clip や ADV のコマンドで、夕焼けの区間はゆっくり、日没後は速く進むようにキーを打つ

## デモの操作と講演との違い

| キー | 動作 |
| --- | --- |
| 1〜9 | シーン切替（時刻・カメラ・露出はそのシーンの既定値に戻る） |
| ↑ / ↓、← / → | パラメータを選ぶ / 増減する（Shift で 4 倍。整数の値は PgUp / PgDn でも変えられる） |
| Z X C V N M | シーンごとのトグル（HUD に表示） |
| `[` / `]` | SkyTime を戻す / 進める（1 秒で 1 時間） |
| T | 時刻の自動再生（速さは Scene 9 の Time Speed） |
| - / = | 露出 |
| 右ドラッグ / WASD / Q E | カメラの向き / 移動 |
| B | ベイクをやり直す（雲 SixWay、SkyOcclusion、LocalGI） |
| G | Scene 8 で建物を「なし → 建築中 → 完成」と切り替える |
| R / H / Esc | トグルを初期値に戻す / HUD の表示切替 / 終了 |

**講演との違い**（デモで簡略化した点）

- 背景はメッシュではなく SDF のレイマーチで描いている。草だけは本物のメッシュを、GPU カリングと間接描画で描いている
- 海のタイル分割は作っていない。区切り方を色で表示するだけ
- プローブは均一なグリッド（17 x 4 x 13 個）で、L1 の球面調和に空の見え具合を焼いている。APV のようなジオメトリに合わせた配置はしていない
- LocalGI は、Cubemap と mip の代わりに 6 方向の色（Ambient Cube）を使う
- 草の配置データは Houdini ではなく、ノイズと道のマスクから生成している（約 5.9 万株）
- ライトシャフトの Distance Scale、大気の Kr / Km など、講演で定義が説明されなかったパラメータは、デモ独自の解釈で実装している
- デモはビルドまでは確認済み。実際の GPU での表示確認はまだで、明るさなどの既定値は要調整の可能性がある
